# `.mbmap` — รูปแบบ Modbus Map เวอร์ชัน 2

ไฟล์ `.mbmap.json` อธิบายแมปรีจิสเตอร์ Modbus ของอุปกรณ์หนึ่งรุ่น ใครเป็นผู้ผลิต สื่อสารกับมันอย่างไร และแต่ละรีจิสเตอร์หมายถึงอะไร เป็นเอกสาร JSON ทุกภาษาจึงอ่านได้ด้วยตัวแยกวิเคราะห์ JSON มาตรฐาน และ [JSON Schema](schema/mbmap-2.schema.json) อธิบายโครงสร้างของมัน

คำสำคัญ **MUST** (ต้อง), **SHOULD** (ควร) และ **MAY** (อาจ) ใช้ตามความหมายใน [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119)

## 1. ตัวอย่าง

```json
{
  "$schema": "https://raw.githubusercontent.com/nobrega8/mbmap-library/main/schema/mbmap-2.schema.json",
  "mbmap": 2,
  "vendor": "Example Corp",
  "model": "EM-100",
  "description": "Single-phase energy meter",
  "protocol": "rtu",
  "unit_id": 1,
  "baudrate": 9600,
  "parity": "E",
  "stopbits": 1,
  "byte_order": "big",
  "word_order": "big",
  "address_base": 0,
  "enums": {
    "relay": {"0": "Open", "1": "Closed"}
  },
  "registers": [
    {"name": "Voltage", "group": "Measurements", "area": "input", "address": 0, "type": "float32", "unit": "V", "description": "RMS voltage"},
    {"name": "Current", "group": "Measurements", "area": "input", "address": 6, "type": "float32", "unit": "A", "description": "RMS current"},
    {"name": "Active energy", "group": "Energy", "area": "holding", "address": 256, "type": "uint32", "scale": 0.01, "unit": "kWh", "word_order": "little"},
    {"name": "Relay state", "group": "Status", "area": "holding", "address": 512, "type": "bool", "bit": 3, "enum": "relay", "description": "Bit 3 of the status word"},
    {"name": "Reset energy", "group": "Commands", "area": "coil", "address": 0, "type": "bool", "access": "W", "description": "Write 1 to reset counters"},
    {"name": "Serial number", "group": "Info", "area": "holding", "address": 1024, "type": "string", "length": 8, "description": "16 ASCII characters"}
  ]
}
```

ตัวอย่างฉบับสมบูรณ์อยู่ที่ [examples/example-corp/em-100.mbmap.json](examples/example-corp/em-100.mbmap.json)

## 2. ไฟล์

- แมปคือออบเจ็กต์ JSON หนึ่งตัว ([RFC 8259](https://www.rfc-editor.org/rfc/rfc8259)) เข้ารหัสเป็น UTF-8 ผู้อ่าน **MUST** ยอมรับและเมิน BOM ที่อยู่ต้นไฟล์ ผู้เขียน **SHOULD NOT** เขียน BOM
- ชื่อไฟล์ลงท้ายด้วย `.mbmap.json`
- ออบเจ็กต์ **MUST NOT** ซ้ำคีย์ ตัวแยกวิเคราะห์ JSON จัดการคีย์ซ้ำต่างกัน ไฟล์ที่มีคีย์ซ้ำจึงไม่ถูกต้อง
- สตริงใช้ตามที่เขียน ไม่มีการตัดช่องว่าง และค่าแบบแจงนับแยกตัวพิมพ์ใหญ่เล็ก (`"holding"` ไม่ใช่ `"Holding"`)
- JSON `null` ไม่ใช่ค่าที่ถูกต้องสำหรับคีย์ใด ให้ละคีย์ไว้แทน
- JSON ไม่มีคอมเมนต์ หมายเหตุเกี่ยวกับทั้งไฟล์ใส่ใน `notes` หมายเหตุเกี่ยวกับรีจิสเตอร์หนึ่งใส่ใน `comment` ของมัน ทั้งสองเป็นข้อความอิสระที่เครื่องมือ **MAY** แสดง และ **MUST NOT** ตีความ
- ผู้เขียน **SHOULD** ใช้รูปแบบใน §1: เยื้องสองช่องว่าง และหนึ่งบรรทัดต่อรีจิสเตอร์และต่อตาราง `enums`/`sentinels` เพื่อให้การเปลี่ยนรีจิสเตอร์หนึ่งตัวต่างกันเพียงบรรทัดเดียว
- `$schema` ไม่บังคับและชี้ตัวแก้ไขไปยัง JSON Schema ผู้อ่าน **MUST** เมินมัน

### 2.1 จำนวนเต็ม

เมื่อค่าเป็น**จำนวนเต็ม** **MAY** เขียนเป็นจำนวนเต็ม JSON (`1040`) หรือสตริงที่เก็บจำนวนเต็มทศนิยมหรือฐานสิบหก `0x` (`"0x0410"`) สตริงรักษาการเขียนแบบฐานสิบหกที่คู่มือใช้กับที่อยู่และตัวระบุ และบรรจุค่า 64 บิตที่ตัวแยกวิเคราะห์ JSON บางตัวอ่านเป็นตัวเลขได้ไม่แม่นยำ (เกิน 2^53) คีย์ของตาราง `enums` และ `sentinels` เป็นสตริงเสมอ ในสองรูปแบบเดียวกัน

### 2.2 ตาราง

**ตาราง**จับคู่ค่าดิบกับป้าย เป็นออบเจ็กต์ที่คีย์เป็นจำนวนเต็มที่เขียนเป็นสตริง (§2.1) และค่าเป็นป้ายที่ไม่ว่าง เช่น `{"0": "Stopped", "1": "Idle", "0xFFFF": "Unimplemented"}` ตารางมีอย่างน้อยหนึ่งรายการ และคีย์สองตัว **MUST NOT** แทนค่าเดียวกัน (`"1"` และ `"0x1"`)

### 3.1 เวอร์ชันของรูปแบบและรีวิชันของแมป

ตัวเลขสองตัวอธิบายแมป และเปลี่ยนด้วยเหตุผลต่างกัน:

- **`mbmap` เวอร์ชันของรูปแบบ** บอกว่าไฟล์ตามข้อกำหนดนี้เวอร์ชันใด เพื่อให้ผู้อ่านรู้ว่าอ่านได้หรือไม่ (§8) แมปทุกแมปที่เขียนตามข้อกำหนดนี้มีค่าเดียวกัน และเปลี่ยนเมื่อรูปแบบเปลี่ยนเท่านั้น
- **`revision` รีวิชันของแมป** บอกว่าไฟล์เป็นฉบับใดของเนื้อหาแมปนี้ เริ่มที่ `1` และ **SHOULD** เพิ่มทีละหนึ่งกับทุกการเปลี่ยนแปลงที่เผยแพร่ซึ่งส่งผลต่อวิธีอ่านหรือเขียนอุปกรณ์ เช่น รีจิสเตอร์ ค่าเริ่มต้นการเชื่อมต่อ ตาราง ช่วงเฟิร์มแวร์ หรือรุ่น **MAY** คงเดิมสำหรับการเปลี่ยนเฉพาะข้อความอิสระ (`description`, `notes`, `comment`, `source`) `revised` ระบุวันที่ของการเปลี่ยนแปลงนั้น

เครื่องมือที่มีแมปเดียวกันสองสำเนา (`vendor` และ `model` เดียวกัน) **SHOULD** ถือว่า `revision` ที่สูงกว่าใหม่กว่า และ **MAY** เสนอฉบับที่ใหม่กว่าให้ผู้ใช้ แมปที่ไม่มี `revision` เปรียบเทียบแบบนี้ไม่ได้ รีวิชันไม่ใช่เวอร์ชันเฟิร์มแวร์ของอุปกรณ์ เฟิร์มแวร์อยู่ใน §3.2

### 3.2 รุ่นและเฟิร์มแวร์

แมปใช้กับรุ่นใน `models` หรือกับ `model` เพียงอย่างเดียวหากไม่มี `models` `model` เป็นชื่อที่แสดงให้คน เป็นอุปกรณ์เดียว หรือชื่อตระกูลหรือซีรีส์เมื่อแมปครอบคลุมหลายตัว (`"PM5100 and PM5300 series"`) ไม่ใช่รายการอุปกรณ์ `models` ระบุทุกชื่อหรือรหัสที่อุปกรณ์รายงานได้ เพื่อให้เครื่องมือเทียบกับอุปกรณ์ที่เชื่อมต่อ (§9):

```json
"model": "PM5100 and PM5300 series",
"models": ["PM5110", "PM5111", "PM5310", "PM5320", "PM5330"]
```

`firmware_min` และ `firmware_max` ระบุว่าแมปใช้กับเฟิร์มแวร์เวอร์ชันใด ทั้งสองเป็นทางเลือก หากไม่มีแมปใช้กับทุกเฟิร์มแวร์ ซึ่งเป็นตัวเลือกที่ถูกต้องเมื่อไม่ทราบเวอร์ชัน `firmware` ยังใช้ได้สำหรับสิ่งที่ช่วงอธิบายไม่ได้ (“2.x ยกเว้น 2.3 beta”)

**สตริงเวอร์ชัน**คือจำนวนเต็มหนึ่งตัวหรือมากกว่าที่คั่นด้วยจุด: `"2"`, `"2.1"`, `"1.02.7"` ส่วนประกอบถูกเทียบเป็นตัวเลขจากซ้าย (`"1.10"` ใหม่กว่า `"1.9"` และ `"1.02"` เท่ากับ `"1.2"`) จึงควรเขียนเวอร์ชันตามที่อุปกรณ์รายงาน ขอบเขตครอบคลุมทุกเวอร์ชันที่ขึ้นต้นด้วยมัน:

- `firmware_min` `"2.1"` รวม `2.1`, `2.1.4` และ `3.0` แต่ไม่รวม `2.0.9`
- `firmware_max` `"2"` รวมทุก `2.x` และ `2.x.y` แต่ไม่รวม `3.0` ส่วน `firmware_max` `"2.3"` รวม `2.3.7` แต่ไม่รวม `2.4`

ดังนั้น `"firmware_min": "1", "firmware_max": "2"` อ่านว่า “เฟิร์มแวร์ 1.x และ 2.x” `firmware_min` **MUST NOT** อยู่หลัง `firmware_max`

**รีจิสเตอร์ที่ขึ้นกับเฟิร์มแวร์** รีจิสเตอร์อาจมี `firmware_min` และ `firmware_max` ของตัวเองด้วยความหมายเดียวกัน เมื่อมันมีอยู่เฉพาะในเฟิร์มแวร์บางเวอร์ชัน ทำให้ใช้ไฟล์เดียวกับเฟิร์มแวร์ที่ต่างกันไม่กี่รีจิสเตอร์ได้ รีจิสเตอร์ที่ไม่มีค่าเหล่านี้ใช้ได้ทุกที่ที่แมปใช้ได้ รีจิสเตอร์สองตัว **MAY** ใช้ `name` (และที่อยู่) เดียวกันได้เมื่อช่วงเฟิร์มแวร์ไม่ซ้อนกัน เครื่องมือใช้ตัวที่ตรงกับอุปกรณ์

ตัวอย่าง: เฟิร์มแวร์ 2.1 ย้ายตัวนับพลังงานและเพิ่มรีจิสเตอร์ตัวประกอบกำลัง:

```json
"firmware_min": "1",
"firmware_max": "2",
"registers": [
  {"name": "Firmware version", "area": "holding", "address": 0, "type": "string", "length": 4, "role": "firmware"},
  {"name": "Voltage", "area": "input", "address": 10, "type": "float32", "unit": "V"},
  {"name": "Active energy", "area": "input", "address": 20, "type": "uint32", "unit": "Wh", "firmware_max": "2.0"},
  {"name": "Active energy", "area": "input", "address": 40, "type": "uint64", "unit": "Wh", "firmware_min": "2.1"},
  {"name": "Power factor", "area": "input", "address": 30, "type": "int16", "scale": 0.001, "firmware_min": "2.1"}
]
```

เมื่อความต่างมาก (ที่อยู่ส่วนใหญ่หรือการตั้งค่าการเชื่อมต่อเปลี่ยน) ไฟล์แยกชัดเจนกว่า คือหนึ่งแมปต่อหนึ่งช่วงเฟิร์มแวร์ แต่ละแมปมี `firmware_min` และ `firmware_max` ของตัวเอง

### 3.3 แหล่งที่มา

`sources` บันทึกเอกสารที่ใช้สร้างหรือใช้ตรวจสอบแมป เพื่อให้ผู้อ่านหาเอกสารเจอและทราบว่าใช้ฉบับใด แต่ละรายการเป็นออบเจ็กต์:

| Key | JSON type | ความหมาย |
|---|---|---|
| `title` | non-empty string, required | ชื่อเอกสาร เช่น `"EM530/EM540 Modbus communication protocol"` |
| `version` | string | ฉบับหรือรีวิชันของเอกสาร ตามที่พิมพ์ไว้บนเอกสาร |
| `date` | string `YYYY`, `YYYY-MM` or `YYYY-MM-DD` | วันที่เผยแพร่ของฉบับนั้น |
| `url` | `http(s)://` URL | ที่ที่พบเอกสาร |
| `note` | string | ส่วนที่ใช้ หรือวิธีตรวจสอบแมป (เช่น `"tables 4.1-4.24"`, `"tested on a device with firmware 2.1"`) |
| `accessed` | string `YYYY-MM-DD` | วันที่ดาวน์โหลดหรืออ่านเอกสาร เพราะเอกสารที่ URL เดิมอาจเปลี่ยนโดยไม่มีเวอร์ชันใหม่ |
| `sha256` | string of 64 hex digits | SHA-256 ของไฟล์ที่ใช้ เพื่อให้ผู้อ่านทราบว่าเอกสารที่ `url` ยังเป็นฉบับเดิมหรือไม่ |

```json
"sources": [
  {"title": "EM530/EM540 Modbus communication protocol", "version": "1.3", "date": "2024-02-13", "url": "https://www.gavazziautomation.com/...", "note": "tables 4.1-4.24", "accessed": "2026-11-14", "sha256": "9f2b…"}
]
```

`sha256` ข้างต้นแสดงแบบย่อ ในไฟล์เป็นเลขฐานสิบหกครบ 64 หลัก เครื่องมือ **MAY** เทียบกับเอกสารที่ดาวน์โหลด และเตือนเมื่อต่างกัน เอกสารถูกอัปเดต และอาจต้องตรวจสอบแมปอีกครั้ง

`source` ยังคงเป็นสรุปบรรทัดเดียวแบบข้อความอิสระสำหรับคน และสำหรับแมปที่ไม่ทราบแหล่งที่มาในรายละเอียดนี้ แมป **MAY** มีทั้งสองอย่าง

## 4. รีจิสเตอร์

แต่ละรายการของ `registers` เป็นออบเจ็กต์ `name`, `area`, `address` และ `type` จำเป็นต้องมี คีย์อื่นทุกตัวเป็นทางเลือก และหากไม่มีจะใช้ค่าเริ่มต้น

| Key | JSON type | Default | ความหมาย |
|---|---|---|---|
| `name` | non-empty string | | ชื่อตัวแปร **SHOULD** ไม่ซ้ำกันในไฟล์ |
| `group` | string | | การจัดกลุ่มอิสระเพื่อแสดงผล (เช่น `Measurements`) |
| `area` | `"coil"`, `"discrete"`, `"input"`, `"holding"` | | พื้นที่ข้อมูล Modbus (§5) |
| `address` | integer (§2.1) | | ที่อยู่ของรีจิสเตอร์ / บิตแรก (§5) |
| `type` | see §6 | | ชนิดข้อมูล |
| `length` | integer ≥ 1 | | จำนวนรีจิสเตอร์ จำเป็นสำหรับ `string` มิฉะนั้นถูกเมิน |
| `bit` | integer `0`–`15` | | สำหรับ `bool` ใน `input`/`holding`: บิตใดของรีจิสเตอร์ 0 = มีนัยสำคัญน้อยสุด สำหรับบิตฟิลด์ `uint16`: บิตต่ำสุดของมัน |
| `bits` | integer `1`–`16` | | สำหรับ `uint16` ใน `input`/`holding`: ความกว้างของบิตฟิลด์ที่เริ่มที่ `bit` (§4.3) |
| `scale` | number | `1` | ตัวคูณ |
| `scale_factor` | string: a register `name` | | รีจิสเตอร์ที่ค่าจำนวนเต็มเป็นเลขชี้กำลังของสิบสำหรับตัวนี้ (§4.4) |
| `offset` | number | `0` | บวกหลังการปรับสเกล |
| `unit` | string | | หน่วยทางวิศวกรรม (`V`, `kWh`, `°C`…) |
| `access` | `"R"`, `"W"`, `"RW"` | `"R"` | การดำเนินการที่อนุญาต |
| `byte_order` | `"big"`, `"little"` | file `byte_order` | แทนที่ค่าเริ่มต้นของไฟล์สำหรับรีจิสเตอร์นี้ (§6) |
| `word_order` | `"big"`, `"little"` | file `word_order` | แทนที่ค่าเริ่มต้นของไฟล์สำหรับรีจิสเตอร์นี้ (§6) |
| `write_min` | number | | ค่าต่ำสุดที่ยอมรับเมื่อเขียน ในหน่วยทางวิศวกรรม (§4.5) |
| `write_max` | number | | ค่าสูงสุดที่ยอมรับเมื่อเขียน ในหน่วยทางวิศวกรรม (§4.5) |
| `enum` | string (a name in `enums`) or table | | ป้ายสำหรับค่าจำนวนเต็มหรือ bool (§4.1) |
| `reference` | see §4.6 | | ค่าดิบที่รีจิสเตอร์นี้ควรเก็บบนอุปกรณ์ที่ปกติดี |
| `firmware_min` | version string (§3.2) | | เฟิร์มแวร์เก่าที่สุดที่มีรีจิสเตอร์นี้ |
| `firmware_max` | version string (§3.2) | | เฟิร์มแวร์ใหม่ที่สุดที่มีรีจิสเตอร์นี้ |
| `role` | `"model"`, `"firmware"`, `"serial"` | | รีจิสเตอร์นี้ระบุตัวอุปกรณ์ (§4.7) |
| `read_alone` | boolean | `false` | รีจิสเตอร์ถูกอ่านในคำขอของตัวเอง (§4.9) |
| `read_group` | non-empty string | | รีจิสเตอร์ถูกอ่านพร้อมรีจิสเตอร์ในกลุ่มเดียวกันเท่านั้น (§4.9) |
| `parts` | array of objects | | ตั้งชื่อค่าภายในรีจิสเตอร์แบบบล็อก เพื่อให้เครื่องมือแสดงและแก้ไขทีละค่า (§4.10) |
| `description` | string | | ข้อความอิสระ |
| `comment` | string | | หมายเหตุอิสระเกี่ยวกับรีจิสเตอร์ สำหรับคนที่แก้ไขแมป |

ค่าทางวิศวกรรม = ดิบ × 10^`scale_factor` × `scale` + `offset` (ถ้าไม่มี `scale_factor`: ดิบ × `scale` + `offset`) เมื่อเขียน เครื่องมือใช้การคำนวณย้อนกลับและปัดเป็นจำนวนเต็มที่ใกล้ที่สุดสำหรับชนิดจำนวนเต็ม

### 4.1 ตารางแปลค่า

หลายรีจิสเตอร์เก็บตัวเลขที่แทนสถานะ: `0` คือหยุด `1` คือว่าง `2` คือกำลังเริ่ม และอื่น ๆ `enum` เปลี่ยนตัวเลขเหล่านั้นเป็นป้าย เป็นอย่างใดอย่างหนึ่ง:

- **ตารางที่เขียนในรีจิสเตอร์**: `"enum": {"0": "Stopped", "1": "Idle", "2": "Starting"}`
- **ชื่อของตาราง**ใน `enums` ระดับบน เพื่อให้รายการเดียวกันถูกเขียนครั้งเดียวสำหรับทุกรีจิสเตอร์ที่ใช้:

```json
"enums": {
  "run_state": {"0": "Stopped", "1": "Idle", "2": "Starting", "3": "Running", "4": "Fault"}
},
"registers": [
  {"name": "Pump 1 state", "area": "holding", "address": 100, "type": "uint16", "enum": "run_state"},
  {"name": "Pump 2 state", "area": "holding", "address": 101, "type": "uint16", "enum": "run_state"}
]
```

ค่าถูกเทียบกับค่า**ดิบ**ก่อน `scale` และ `offset` ค่าที่ไม่อยู่ในตารางแสดงเป็นตัวเลขธรรมดา เครื่องมือ **SHOULD** เสนอป้ายเมื่อเขียน

### 4.2 ค่าเซนทิเนล

อุปกรณ์บางตัวตอบด้วยค่าดิบที่สงวนไว้แทนค่าที่วัดได้ ค่าหนึ่งหมายถึง “ไม่ได้ใช้งาน” อีกค่า “เกินช่วง” อีกค่า “เซนเซอร์เสีย” `sentinels` ประกาศค่าเหล่านี้สำหรับทุกรีจิสเตอร์ของชนิดหนึ่ง:

```json
"sentinels": {
  "uint16": {"0xFFFF": "Unimplemented", "0xFFFE": "Over range", "0xFFFD": "Under range"},
  "int16": {"0x7FFF": "Unimplemented", "0x7FFE": "Over range", "0x7FFD": "Under range"},
  "uint32": {"0xFFFFFFFF": "Unimplemented"}
}
```

- คีย์ของ `sentinels` คือ `int16`, `uint16`, `int32`, `uint32`, `int64`, `uint64` ตารางใช้กับทุกรีจิสเตอร์ของชนิดนั้น
- ค่า **MUST** พอดีกับชนิด และถูกเทียบกับค่า**ดิบ**ก่อน `scale` และ `offset`
- เมื่อค่าที่อ่านตรงกัน เครื่องมือ **SHOULD** แสดงป้ายแทนตัวเลข และ **SHOULD NOT** ถือเป็นค่าที่วัดได้ (ในกราฟ ขีดจำกัด หรือค่าเฉลี่ย)
- ป้าย `enum` สำหรับค่าดิบเดียวกันมีลำดับความสำคัญเหนือเซนทิเนล

### 4.3 บิตฟิลด์

อุปกรณ์บางตัวอัดค่าเล็ก ๆ หลายค่าลงในรีจิสเตอร์เดียว เช่น รหัสสัญญาณเตือน 4 บิตสี่ตัว รีจิสเตอร์ `uint16` ที่มี `bit` และ `bits` อ่านหนึ่งในนั้น: ค่าดิบ = (รีจิสเตอร์ >> `bit`) & (2^`bits` − 1) `bit` + `bits` **MUST NOT** เกิน 16

```json
{"name": "Alarm A", "area": "holding", "address": 100, "type": "uint16", "bit": 12, "bits": 4, "enum": "alarm_condition"},
{"name": "Alarm B", "area": "holding", "address": 100, "type": "uint16", "bit": 8, "bits": 4, "enum": "alarm_condition"}
```

รีจิสเตอร์ที่อ่านฟิลด์ต่างกันของรีจิสเตอร์เดียวกันไม่ซ้อนกัน การเขียนฟิลด์ **SHOULD** อ่านรีจิสเตอร์ เปลี่ยนเฉพาะบิตของฟิลด์ แล้วเขียนกลับ

### 4.4 ตัวคูณสเกล

อุปกรณ์บางตัว โดยเฉพาะอินเวอร์เตอร์และมิเตอร์ SunSpec ส่งรีจิสเตอร์เลขชี้กำลังแยกสำหรับค่าแทนสเกลคงที่: ค่าคือดิบ × 10^เลขชี้กำลัง และเลขชี้กำลังเปลี่ยนไปตามช่วงของอุปกรณ์ได้ `scale_factor` ระบุชื่อรีจิสเตอร์เลขชี้กำลังนั้น:

```json
{"name": "AC power", "area": "holding", "address": 40083, "type": "int16", "unit": "W", "scale_factor": "W_SF"},
{"name": "W_SF", "area": "holding", "address": 40084, "type": "int16"}
```

- รีจิสเตอร์ที่ระบุ **MUST** เป็นรีจิสเตอร์ของไฟล์เดียวกันที่มีชนิดจำนวนเต็ม (`int16` … `uint64`) และไม่มี `bits` และ **MUST NOT** มี `scale_factor` เอง หากหลายรีจิสเตอร์ใช้ชื่อเดียวกัน ตัวแรกมีผล
- เฉพาะชนิดตัวเลขเท่านั้นที่มี `scale_factor` ได้ (ไม่ใช่ `bool` หรือ `string`)
- เครื่องมืออ่านรีจิสเตอร์เลขชี้กำลังพร้อมกับค่า แม้ผู้ใช้เลือกไม่แสดง หากอ่านเลขชี้กำลังไม่ได้ หรือเป็นเซนทิเนล (§4.2 เช่น `-32768` ของ SunSpec = ไม่ได้ใช้งาน) ค่าจะใช้ไม่ได้
- เมื่อเขียน เครื่องมืออ่านเลขชี้กำลังก่อนแล้วคำนวณย้อนกลับ

### 4.5 ขีดจำกัดการเขียน

`write_min` และ `write_max` ประกาศว่ารีจิสเตอร์ยอมรับค่าใดเมื่อเขียน เพื่อให้เครื่องมือปฏิเสธค่าที่ไม่ดีก่อนถึงอุปกรณ์

- ทั้งสองเป็นตัวเลขใน**หน่วยทางวิศวกรรม** คือค่าที่ผู้ใช้เห็นหลังใช้ `scale_factor`, `scale` และ `offset` ขีดจำกัด `0.5` บนรีจิสเตอร์ที่มี `scale` `0.1` หมายถึงค่าดิบ 5
- ละได้ทั้งสองอย่าง ขีดจำกัดที่ขาดทำให้ด้านนั้นเปิด หากขาดทั้งสอง รีจิสเตอร์ไม่มีขีดจำกัดที่ประกาศ (อุปกรณ์เป็นผู้ตัดสิน)
- `write_min` **MUST NOT** มากกว่า `write_max` ขีดจำกัดรวมค่าขอบ
- เครื่องมือ **MUST NOT** ส่งการเขียนที่ค่าทางวิศวกรรมต่ำกว่า `write_min` หรือสูงกว่า `write_max` และ **SHOULD** บอกผู้ใช้ว่าเกินขีดจำกัดใด
- ใช้กับค่าที่ผู้ใช้ขอ ก่อนแปลงเป็นค่าดิบและปัดเศษ ค่าที่อยู่ในขีดจำกัดแต่ยังไม่พอดีกับชนิดของรีจิสเตอร์ จะถูกปฏิเสธโดยการตรวจชนิดปกติ
- ไม่มีความหมายสำหรับรีจิสเตอร์ `bool` และ `string` หรือรีจิสเตอร์ที่เขียนไม่ได้ (`access` `"R"`) และถูกเมินที่นั่น

```json
{"name": "Setpoint", "area": "holding", "address": 100, "type": "uint16", "scale": 0.1, "unit": "°C", "access": "RW", "write_min": 5, "write_max": 30}
```

### 4.6 ค่าอ้างอิง

`reference` ให้ค่าที่รู้ว่าอุปกรณ์ปกติเก็บไว้ในรีจิสเตอร์นี้ (หมายเลขรุ่น ตัวระบุโปรโตคอลคงที่ รหัสผู้ผลิต) เครื่องมืออ่านรีจิสเตอร์แล้วเทียบกับค่าอ้างอิง เพื่อตรวจพบที่อยู่ ฐาน ลำดับไบต์ หรือชนิดข้อมูลที่ผิด ก่อนที่ผู้ใช้จะเชื่อค่าอื่น ไม่ใช่ทุกอุปกรณ์ที่มีรีจิสเตอร์เช่นนี้ รีจิสเตอร์ส่วนใหญ่จึงไม่มี `reference`

- เป็นค่า**ดิบ**ก่อน `scale_factor`, `scale` และ `offset` ในชนิด JSON ของค่านั้น: จำนวนเต็ม (§2.1) สำหรับชนิดจำนวนเต็มและบิตฟิลด์ ตัวเลขสำหรับ `float32` และ `float64` `true` / `false` สำหรับ `bool` สตริงสำหรับ `string` **MUST** พอดีกับชนิด (และความกว้างของบิตฟิลด์ หรือ `2 × length` ตัวอักษรสำหรับสตริง)
- การตรวจคือตัวรีจิสเตอร์เอง: เครื่องมืออ่าน `area` และ `address` ของมัน (ปรับตาม `address_base` แล้ว) และถอดรหัส `type` ด้วยลำดับไบต์และเวิร์ด
- แมปมีรีจิสเตอร์ที่มี `reference` กี่ตัวก็ได้
- ผลของแต่ละการตรวจ: **match** (ค่าดิบที่ถอดรหัสเท่ากับค่าอ้างอิง), **mismatch** (ต่างกัน), **failed** (การอ่านส่งข้อผิดพลาดหรือหมดเวลา จึงไม่ทราบอะไร), **not checked** (ไม่ได้อ่านรีจิสเตอร์) เครื่องมือ **SHOULD** รายงานแยกกัน mismatch ชี้ไปที่แมปหรือการตั้งค่าที่ผิด failed ชี้ไปที่ปัญหาการเชื่อมต่อหรือการระบุที่อยู่
- float เทียบที่ความแม่นยำของชนิดเอง (ค่าอ้างอิง `float32` เทียบเป็น float 32 บิต) สตริงเทียบหลังตัด NUL และช่องว่างท้าย
- ค่าอ้างอิงเป็นเพียงตัวช่วยวินิจฉัย ลำดับไบต์หรือเวิร์ดหลายแบบอาจถอดรหัสไบต์เดียวกันเป็นค่าเดียวกัน (ตัวเลขเล็กหรือพาลินโดรมอ่านเหมือนกันในมากกว่าหนึ่งลำดับ) การตรงกันจึงไม่พิสูจน์ว่าทั้งแมปถูกต้อง แมป **SHOULD** ใช้ค่าที่โดดเด่น และ **SHOULD** ให้มากกว่าหนึ่งค่าเมื่ออุปกรณ์มี
- `reference` บนรีจิสเตอร์ที่อ่านไม่ได้ (`access` `"W"`) เป็นข้อผิดพลาด

```json
{"name": "Manufacturer code", "area": "holding", "address": 768, "type": "uint16", "reference": "0x016A"},
{"name": "Serial prefix", "area": "holding", "address": 770, "type": "uint32", "word_order": "little", "reference": "0x00010002"}
```

### 4.7 รีจิสเตอร์ระบุตัวตน

`role` ทำเครื่องหมายรีจิสเตอร์ที่บอกว่าเชื่อมต่อกับอุปกรณ์ใด เพื่อให้เครื่องมือตรวจแมปเทียบกับมัน (§9):

- **`"model"`**: ชื่อหรือรหัสรุ่นของอุปกรณ์ ค่าของมัน หรือป้าย `enum` หากมี ถูกเทียบกับ `models` รหัสรุ่นที่เป็นตัวเลขควรมีป้าย: `"enum": {"0x016A": "EM-100"}`
- **`"firmware"`**: เวอร์ชันเฟิร์มแวร์ รีจิสเตอร์สตริงถูกอ่านเป็นข้อความ และใช้สตริงเวอร์ชันแรกในนั้น (`"V2.01b"` ได้ `2.01`) ตัวเลขให้ค่าทางวิศวกรรม (`102` กับ `scale` `0.01` ได้ `1.02`) เมื่อหลายรีจิสเตอร์มีบทบาทนี้ ค่าของมันถูกต่อด้วยจุดตามลำดับในไฟล์ เหมาะกับอุปกรณ์ที่เก็บเวอร์ชันหลักและรองแยกกัน เช่น เป็นบิตฟิลด์สองตัวของรีจิสเตอร์เดียว (`"bit": 8, "bits": 8` และ `"bit": 0, "bits": 8`)
- **`"serial"`**: หมายเลขซีเรียล เครื่องมือ **MAY** แสดง และไม่เคยนำไปเปรียบเทียบ

รีจิสเตอร์อย่างมากหนึ่งตัว **MAY** มีบทบาท `"model"` และอย่างมากหนึ่งตัว `"serial"` รีจิสเตอร์ที่มีบทบาท **MUST** อ่านได้ นอกจากนั้นรีจิสเตอร์ที่มีบทบาทเป็นรีจิสเตอร์ธรรมดา ถูกอ่านและแสดงเหมือนตัวอื่น และมี `reference` ได้ด้วย

### 4.8 ตัวตนจากอุปกรณ์ (FC17, FC43)

อุปกรณ์บางตัวรายงานว่าตัวเองคืออะไรด้วยฟังก์ชันของตัวเอง และไม่มีรีจิสเตอร์ระบุตัวตน `identify` บอกว่าต้องส่งฟังก์ชันใดและตัวตนอยู่ที่ใดในคำตอบ เพื่อให้เครื่องมือตรวจแมปได้แบบรีจิสเตอร์ใน §4.7 (§9) แมปมี `identify` อย่างมากหนึ่งตัว

```json
"enums": {"type_codes": {"0x41": "DMG610", "0x57": "DMG620"}},
"identify": {
  "function": 17,
  "fields": [
    {"name": "Type", "offset": 0, "type": "uint8", "role": "model", "enum": "type_codes"},
    {"name": "Software revision", "offset": 1, "type": "uint8", "role": "firmware"},
    {"name": "Hardware revision", "offset": 2, "type": "uint8"}
  ]
}
```

```json
"identify": {
  "function": 43,
  "fields": [
    {"name": "Vendor name", "object": 0},
    {"name": "Product code", "object": 1, "role": "model"},
    {"name": "Revision", "object": 2, "role": "firmware"}
  ]
}
```

| Key | JSON type | Default | ความหมาย |
|---|---|---|---|
| `function` | `17` or `43` | | `17`: Report Slave ID `43`: Read Device Identification (encapsulated interface transport, ชนิด MEI `0x0E`) |
| `fields` | non-empty array of field objects | | ค่าที่จะดึงจากคำตอบ |

แต่ละฟิลด์เป็นออบเจ็กต์ `name` จำเป็นเสมอ `role` และคีย์ด้านล่างขึ้นกับ `function`

| Key | JSON type | Default | ความหมาย |
|---|---|---|---|
| `name` | non-empty string | | ชื่อที่แสดงให้คน |
| `role` | `"model"`, `"firmware"`, `"serial"` | | ความหมายของค่า เหมือนรีจิสเตอร์ (§4.7) อย่างมากหนึ่ง `"model"` และหนึ่ง `"serial"` |
| `offset` | integer ≥ 0 | | **FC17 เท่านั้น จำเป็น** ตำแหน่งของฟิลด์เป็นไบต์ในข้อมูลของคำตอบ ออฟเซ็ต `0` คือไบต์แรกหลังจำนวนไบต์ ข้อมูลจึงเป็นไบต์ที่อุปกรณ์ระบุหลัง “byte count” ในคู่มือ |
| `type` | `"uint8"`, `"uint16"`, `"string"` | | **FC17 เท่านั้น จำเป็น** `uint16` เป็น big-endian `string` เป็น ASCII ตัด NUL และช่องว่างท้าย |
| `length` | integer ≥ 1 | | **FC17 เท่านั้น** ความยาวเป็นไบต์ จำเป็นสำหรับ `string` |
| `enum` | table name or inline table | | **FC17 เท่านั้น** แปลตัวเลขเป็นป้าย (§4.1) รหัสรุ่นควรมีป้าย ซึ่งจะถูกเทียบกับ `models` |
| `object` | integer 0–255 | | **FC43 เท่านั้น จำเป็น** id ออบเจ็กต์: `0x00` VendorName, `0x01` ProductCode, `0x02` MajorMinorRevision, `0x03` VendorUrl, `0x04` ProductName, `0x05` ModelName, `0x06` UserApplicationName, `0x80`–`0xFF` อุปกรณ์กำหนดเอง |

- **FC43:** ค่าของออบเจ็กต์เป็นสตริง ASCII ตัด NUL และช่องว่างท้าย เครื่องมือขอระดับการเข้าถึง (basic, regular หรือ extended) ที่รวมทุกออบเจ็กต์ที่ฟิลด์ระบุ และตามแฟล็ก “more follows” จนครบ สำหรับ `"firmware"` ใช้สตริงเวอร์ชันแรกในข้อความ เหมือนรีจิสเตอร์สตริง (§4.7)
- **ทั้งสองฟังก์ชัน:** อุปกรณ์ตอบตาม unit id ไม่ใช่ที่อยู่รีจิสเตอร์ `address_base` จึงไม่ใช้
- **ไม่มีค่า:** คำตอบที่สั้นกว่าที่ฟิลด์ต้องการ คำตอบแบบข้อยกเว้น ออบเจ็กต์ที่ขาด หรืออุปกรณ์ที่ไม่รองรับฟังก์ชัน ไม่ให้ค่า การตรวจเป็น **unknown** (§9) ไม่ใช่ mismatch
- **หลายแหล่ง:** `identify` และรีจิสเตอร์ที่มี `role` มีด้วยกันได้ เมื่อทั้งสองให้ค่าสำหรับบทบาทเดียวกัน เครื่องมือ **SHOULD** ใช้รีจิสเตอร์ และ **MAY** ใช้ `identify` สำหรับบทบาทที่ไม่มีรีจิสเตอร์ให้

### 4.9 การอ่านในคำขอแยก

ผู้อ่านมักรวมรีจิสเตอร์ที่อยู่ติดกันเป็นคำขอเดียว อุปกรณ์บางตัวปฏิเสธคำขอที่ข้ามเส้นแบ่งระหว่างสองตารางภายใน แม้ทุกรีจิสเตอร์ในนั้นมีอยู่ คีย์ทางเลือกสองตัวจำกัดการรวมรีจิสเตอร์:

- **`read_alone`**: `true` หมายถึงรีจิสเตอร์ถูกอ่านในคำขอที่ไม่มีรีจิสเตอร์อื่น บิตฟิลด์และรีจิสเตอร์อื่นที่ครอบครองเวิร์ดเดียวกันถือเป็นรีจิสเตอร์เดียวกัน
- **`read_group`**: ชื่อ รีจิสเตอร์ที่มีชื่อเดียวกัน **MAY** ถูกอ่านในคำขอเดียว และคำขอ **MUST NOT** มีรีจิสเตอร์ต่างกลุ่มหรือรีจิสเตอร์ที่ไม่มีกลุ่ม รีจิสเตอร์ที่ไม่มี `read_group` ถูกรวมเหมือนเดิม

```json
{"name": "Digital input status", "area": "holding", "address": 768, "type": "uint16", "read_group": "status"},
{"name": "Active tariff", "area": "holding", "address": 769, "type": "uint16", "read_group": "status"},
{"name": "Firmware", "area": "holding", "address": 770, "type": "uint16", "read_alone": true}
```

เมื่อมีทั้งสองคีย์ `read_alone` ชนะ คีย์เหล่านี้จำกัดเฉพาะการรวม ผู้อ่านจะทำคำขอมากกว่าที่จำเป็นก็ได้ และ `max_read_registers` กับ `max_read_bits` ยังใช้อยู่ คีย์เหล่านี้ส่งผลต่อวิธีขอรีจิสเตอร์เท่านั้น ไม่ใช่ความหมายของมัน ผู้อ่านที่ไม่รู้จักคีย์จึงอ่านรีจิสเตอร์เดียวกัน รวมแบบที่เคยทำ นั่นเป็นเหตุผลที่ไม่ต้องใช้ `mbmap` เวอร์ชันใหม่ (§8) บนอุปกรณ์ที่ปฏิเสธคำขอที่รวมแล้ว ผู้อ่านเก่าล้มเหลวเหมือนที่จะเป็นหากไม่มีคีย์

### 4.10 ส่วนของบล็อก

อุปกรณ์บางตัวเก็บหลายค่าในบล็อกเดียวและรับเฉพาะบล็อกทั้งก้อน การเขียนที่เริ่มกลางบล็อกหรือไม่ครอบคลุมบล็อกจะถูกปฏิเสธ (ข้อยกเว้น `0x02` หรือ `0x03`) กรณีทั่วไปคือเกตเวย์ SMS ที่บล็อกเก็บหมายเลขผู้รับตามด้วยข้อความ แมปอธิบายบล็อกนั้นเป็นรีจิสเตอร์ **หนึ่งตัว** เหมือนที่เคยเป็น และ `parts` บอกว่าข้างในมีอะไร:

```json
{
  "name": "Add SMS", "area": "holding", "address": 397, "type": "string", "length": 90, "access": "RW",
  "parts": [
    {"name": "Recipient", "offset": 0, "length": 10, "description": "Phone number as 00 + digits (00 stands for +)"},
    {"name": "Text", "offset": 10, "length": 80}
  ]
}
```

| Key | JSON type | Default | ความหมาย |
|---|---|---|---|
| `name` | non-empty string | | ชื่อที่แสดงให้คน |
| `offset` | integer ≥ 0 | | ตำแหน่งของส่วนในบล็อก เป็น**รีจิสเตอร์**นับจากรีจิสเตอร์แรกของรีจิสเตอร์ |
| `type` | `"string"` or a numeric type (§6) | `"string"` | วิธีอ่านและเขียนส่วนนั้น |
| `length` | integer ≥ 1 | | จำนวนรีจิสเตอร์ จำเป็นสำหรับ `string` ถูกเมินสำหรับชนิดอื่น |
| `description` | string | | ข้อความอิสระ |

- `parts` ใช้กับรีจิสเตอร์ `string` เท่านั้น **MUST NOT** ว่าง ทุกส่วน **MUST** อยู่ในบล็อก (`offset` บวกรีจิสเตอร์ของมันไม่เกิน `length` ของรีจิสเตอร์) และส่วนต่าง ๆ **MUST NOT** ซ้อนกัน รีจิสเตอร์ที่ไม่มีส่วนใดครอบคลุมอนุญาตได้ คือส่วนเติม
- ตัวรีจิสเตอร์ยังคงความหมายเดิม ผู้อ่านที่ไม่รู้จัก `parts` อ่านและเขียนทั้งบล็อกเป็นสตริงเดียวในคำขอเดียวเหมือนเดิม แมปเช่นนี้จึงใช้ได้ในทุกเครื่องมือ
- เครื่องมือที่รู้จัก `parts` **SHOULD** แสดงแต่ละส่วนเป็นฟิลด์ของตัวเอง เมื่ออ่านจะถอดรหัสแต่ละส่วนจากบล็อกด้วย `byte_order` และ `word_order` ของรีจิสเตอร์ (§6) เมื่อเขียนจะสร้างบล็อก**ทั้งหมด**จากส่วนต่าง ๆ และส่งในคำขอเดียว (FC16) ส่วนที่ผู้ใช้เว้นว่างถูกส่งเป็นไบต์ศูนย์ ฟิลด์ว่างจึงไม่เก็บค่าเก่าโดยบังเอิญ เครื่องมือ **MUST NOT** ส่งการเขียนที่ครอบคลุมเพียงบางส่วน เพราะอุปกรณ์จะปฏิเสธ
- ส่วน `string` เป็น ASCII เติมด้วย NUL จนถึง `length` เครื่องมือ **MUST** ปฏิเสธข้อความที่ยาวกว่า `2 × length` ตัวอักษร ส่วนตัวเลขถูกเข้ารหัสตามปกติ (§6)
- `access` เป็นของรีจิสเตอร์ ส่วนต่าง ๆ เขียนได้มากกว่าบล็อกไม่ได้
- `parts` อธิบายเพียงว่าข้างในรีจิสเตอร์มีอะไร จึงไม่ต้องใช้ `mbmap` เวอร์ชันใหม่ (§8) ผู้อ่านที่เมินมันทำงานเหมือนเดิม

## 5. พื้นที่และที่อยู่

| `area` | หน่วย | อ่าน | เขียน | `access` ที่อนุญาต |
|---|---|---|---|---|
| `coil` | บิต | FC01 | FC05 / FC15 | `R`, `W`, `RW` |
| `discrete` | บิต | FC02 | — | `R` |
| `input` | รีจิสเตอร์ 16 บิต | FC04 | — | `R` |
| `holding` | รีจิสเตอร์ 16 บิต | FC03 | FC06 / FC16 | `R`, `W`, `RW` |

เมื่อ `address_base` เป็น `0` `address` คือที่อยู่ที่ส่งบนสาย (0–65535) เมื่อ `address_base` เป็น `1` ที่อยู่บนสายคือ `address − 1` (1–65536) ซึ่งตรงกับคู่มือที่นับรีจิสเตอร์จาก 1

การเขียนแบบ “Modicon” 5 และ 6 หลัก (`40001`, `300010`) **ไม่ถูกต้อง**ใน `address` ให้เขียนเป็นพื้นที่บวกตัวเลข: `40001` กลายเป็น `"area": "holding"`, `"address": 1` พร้อม `"address_base": 1`

## 6. ชนิด ลำดับไบต์ และลำดับเวิร์ด

| `type` | รีจิสเตอร์ | หมายเหตุ |
|---|---|---|
| `bool` | — | ใน `coil`/`discrete`: หนึ่งบิต ใน `input`/`holding`: หนึ่งบิตของรีจิสเตอร์ จึงต้องมี `bit` |
| `int16`, `uint16` | 1 | |
| `int32`, `uint32`, `float32` | 2 | float เป็น IEEE 754 |
| `int64`, `uint64`, `float64` | 4 | |
| `string` | `length` | ASCII 2 ตัวอักษรต่อรีจิสเตอร์ NUL และช่องว่างท้ายถูกตัดเมื่ออ่าน |

การตั้งค่าอิสระสองอย่างกำหนดว่าไบต์ของค่ามาถึงอย่างไร:

- **`byte_order`** ภายในแต่ละรีจิสเตอร์ 16 บิต: `"big"` ส่งไบต์สูงก่อน (มาตรฐาน Modbus) `"little"` ส่งไบต์ต่ำก่อน
- **`word_order`** ข้ามรีจิสเตอร์ของค่า 32 บิตหรือ 64 บิต: `"big"` วางรีจิสเตอร์ที่มีนัยสำคัญสูงสุดก่อน (ที่อยู่ต่ำสุด) `"little"` วางรีจิสเตอร์ที่มีนัยสำคัญต่ำสุดก่อน

คีย์ระดับบนกำหนดค่าเริ่มต้นของไฟล์ `byte_order` และ `word_order` ของรีจิสเตอร์แทนที่ได้ทีละอย่าง (รีจิสเตอร์ที่ตั้งเพียง `"word_order": "little"` ยังคงลำดับไบต์ของไฟล์)

| ชนิด | `byte_order` | `word_order` |
|---|---|---|
| `bool` | ไม่ใช้ | ไม่ใช้ |
| `int16`, `uint16` | สลับสองไบต์ของรีจิสเตอร์ | ไม่ใช้ (หนึ่งรีจิสเตอร์) |
| `int32`, `uint32`, `float32` | สลับสองไบต์ของแต่ละรีจิสเตอร์ | กำหนดว่ารีจิสเตอร์ใดในสองตัวเป็นเวิร์ดสูง |
| `int64`, `uint64`, `float64` | สลับสองไบต์ของแต่ละรีจิสเตอร์ | `"little"` กลับลำดับสี่รีจิสเตอร์ทั้งชุด |
| `string` | `"big"`: ไบต์แรกที่ได้รับเป็นตัวอักษรแรก `"little"`: ไบต์ที่สองที่ได้รับเป็นตัวอักษรแรก | ไม่ใช้ (รีจิสเตอร์ถูกอ่านตามลำดับที่อยู่) |

สำหรับค่า 64 บิต ลำดับเวิร์ดแบบ little กลับลำดับทั้งชุดของสี่รีจิสเตอร์ ไม่ได้สลับครึ่ง 32 บิตสองส่วนแยกกัน

ลำดับบนสายของค่า 32 บิต `0x0A0B0C0D`:

| `byte_order` | `word_order` | ไบต์บนสาย | ชื่อทั่วไป |
|---|---|---|---|
| `big` | `big` | `0A 0B 0C 0D` | มาตรฐาน Modbus |
| `big` | `little` | `0C 0D 0A 0B` | “สลับเวิร์ด” ใช้ในมิเตอร์และ PLC จำนวนมาก |
| `little` | `big` | `0B 0A 0D 0C` | “สลับไบต์” (พบน้อย) |
| `little` | `little` | `0D 0C 0B 0A` | little-endian |

## 7. การตรวจสอบ

ผู้อ่าน **SHOULD** รายงานทุกปัญหาด้วยรหัสด้านล่างรหัสใดรหัสหนึ่งและ [JSON Pointer](https://www.rfc-editor.org/rfc/rfc6901) ไปยังค่า (`/registers/3/address`, `/enums/relay`) เพื่อให้เครื่องมือเห็นตรงกันว่าอะไรผิด ปัญหาของทั้งไฟล์ไม่มี pointer **error** ทำให้ไฟล์ไม่ถูกต้อง **warning** ถูกรายงาน แต่ไฟล์ยังใช้ได้

[JSON Schema](schema/mbmap-2.schema.json) ตรวจโครงสร้าง ชนิด JSON และช่วงของค่า กฎที่เชื่อมหลายค่า (`unknown-enum`, ตัวคูณสเกล, `overlap`, `address-range`, `bad-reference` ตามชนิด, คีย์ซ้ำ) ต้องใช้โค้ด โฟลเดอร์ [`tests/`](tests/) มีไฟล์ตัวอย่างพร้อมการวินิจฉัยที่แต่ละไฟล์ต้องให้ เพื่อให้ทุกการสร้างตรวจตัวเองเทียบกับมันได้

## 8. ความเข้ากันได้และการกำหนดเวอร์ชัน

- ผู้อ่าน **MUST** เมินคีย์ที่ไม่รู้จัก ทั้งระดับบนและในรีจิสเตอร์ ทำให้ไฟล์ใหม่เปิดในผู้อ่านเก่าได้
- คีย์เฉพาะของผู้ผลิตหรือเครื่องมือ **SHOULD** ขึ้นต้นด้วย `x_` (`"x_modbench_icon"`, `"x_alarm_high"`) เพื่อไม่ชนกับข้อกำหนดเวอร์ชันอนาคต ค่าของมัน **MAY** เป็นชนิด JSON ใดก็ได้
- `mbmap` คือเวอร์ชัน**หลัก** ผู้อ่าน **MUST** ปฏิเสธไฟล์ที่ `mbmap` ไม่รองรับ และ **SHOULD** บอกว่าพบเวอร์ชันใด
- คีย์ทางเลือกใหม่ที่ผู้อ่านเก่าเมินได้อย่างปลอดภัยเพิ่มได้โดยไม่เปลี่ยน `mbmap` คีย์ที่ผู้อ่านเก่าจะเข้าใจความหมายผิดหากเมินมัน ต้องใช้เวอร์ชันหลักใหม่
- ไฟล์สคีมาตั้งชื่อตามเวอร์ชันหลัก (`mbmap-2.schema.json`) และได้เพียงคีย์ทางเลือกภายในนั้น

## 9. การตรวจแมปกับอุปกรณ์ที่เชื่อมต่อ

เครื่องมือที่อ่านรีจิสเตอร์ระบุตัวตน (§4.7) หรือคำตอบระบุตัวตนที่ `identify` (§4.8) อธิบาย จากอุปกรณ์ที่เชื่อมต่อ **SHOULD** เทียบกับแมป เพื่อไม่ให้ผู้ใช้เชื่อค่าจากแมปที่เขียนสำหรับรุ่นหรือเฟิร์มแวร์อื่น และอาจให้ผู้ใช้ระบุรุ่นหรือเฟิร์มแวร์เองเมื่ออุปกรณ์ไม่รายงาน

แต่ละการตรวจมีผลหนึ่งในสามอย่าง:

| ผล | รุ่น | เฟิร์มแวร์ |
|---|---|---|
| **match** | รุ่นของอุปกรณ์ เทียบโดยไม่สนตัวพิมพ์และช่องว่างรอบ ๆ เป็นหนึ่งใน `models` (หรือ `model`) | เวอร์ชันของอุปกรณ์อยู่ใน `firmware_min` … `firmware_max` |
| **mismatch** | ไม่ใช่ | อยู่นอกช่วง |
| **unknown** | แมปไม่มีรีจิสเตอร์ `"model"` อ่านไม่ได้ หรือไม่ให้ค่า | แมปไม่มีรีจิสเตอร์ `"firmware"` อ่านไม่ได้ หาสตริงเวอร์ชันในนั้นไม่เจอ หรือแมปไม่ได้ประกาศช่วง |

สิ่งที่เครื่องมือทำกับแต่ละผล:

- **match**: ไม่มีอะไรต้องรายงาน เครื่องมือ **MAY** แสดงว่าจำอุปกรณ์ได้
- **mismatch**: เครื่องมือ **SHOULD** เตือนอย่างชัดเจน บอกว่าแมปคาดหวังอะไรและอุปกรณ์รายงานอะไร และ **SHOULD** ขอการยืนยันก่อนเขียนครั้งแรกลงอุปกรณ์ **MUST NOT** หยุดอ่านเพราะเรื่องนี้ การอ่านไม่เป็นอันตราย และผู้ใช้อาจรู้ดีกว่า (อุปกรณ์เปลี่ยนแบรนด์ เฟิร์มแวร์ใหม่ที่ใช้รีจิสเตอร์เดิม)
- **unknown**: ไม่ใช่ปัญหา อุปกรณ์ส่วนใหญ่ไม่รายงานรุ่นหรือเฟิร์มแวร์ และแมปส่วนใหญ่ใช้ได้กับทุกเฟิร์มแวร์ เครื่องมือ **MUST NOT** ถือเป็น mismatch และ **MAY** กล่าวถึงว่าแมปประกาศช่วงเฟิร์มแวร์ที่ตรวจไม่ได้

รีจิสเตอร์ที่มีช่วงเฟิร์มแวร์ของตัวเอง (§3.2):

- เมื่อ**ทราบ**เฟิร์มแวร์ เครื่องมือ **SHOULD** ใช้เฉพาะรีจิสเตอร์ที่ช่วงครอบคลุม ตัวอื่นไม่มีบนอุปกรณ์นี้ และชื่อรีจิสเตอร์ที่ใช้ร่วมกันหลายช่วงเฟิร์มแวร์หมายถึงรีจิสเตอร์เดียว
- เมื่อ**ไม่ทราบ**เฟิร์มแวร์ เครื่องมือ **SHOULD** อ่านทุกรีจิสเตอร์ และ **SHOULD** แสดงว่าตัวใดขึ้นกับเฟิร์มแวร์ (เช่น “เฟิร์มแวร์ 2.1 ขึ้นไป”) และ **MAY** ให้ผู้ใช้เลือกเวอร์ชัน

แมปที่ไม่มี `models`, `firmware_min`, `firmware_max` และรีจิสเตอร์ระบุตัวตนจะไม่ถูกตรวจกับอะไร ซึ่งถูกต้องสำหรับแมปที่ใช้กับทุกอุปกรณ์ของรุ่นนั้น
